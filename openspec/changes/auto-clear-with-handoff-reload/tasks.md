## 9. Discovered live during the first real clears (2026-09-12 evening) — follow-ups

- [x] 9.1 **Worktree blindness (measured, FIXED 2026-09-13):** a fleet-held agent working a worktree writes its handoff into the WORKTREE's `.set/handoff/`; a `/clear` reinject resolving from the process cwd (main repo) never sees it and loads a different thread's handoff by mtime. Live case: clear of the consumer's `the fleet-held agent` reloaded `0912-a16a` (main repo) while the thread's real state was `0912-ff48` in the consumer worktree. **Fix (both reinject copies):** candidate dirs = the session's cwd tree + every `git worktree list` sibling; PRIMARY choice = the session's own `.written-<session8>` arm marker wherever it lives (names the exact file); fallback = newest-by-mtime of the CWD'S OWN TREE ONLY — a first attempt that merged all trees into one mtime pool was caught live the same morning (the bugfix pane, main cwd, received the wt-ai page because it was newer) and reverted; sibling pages stay reachable, listed by full path. Both live cases dry-run verified; fixture tests in `test/reinject-clear.test.mjs`. **Write-side twin fixed the same hour (measured live):** the consumer's PostToolUse `handoff-write-check.mjs` armed `.written-<session8>` in the MAIN repo's dir while the handoff it validated sat in the worktree — a 542k wt-ai thread ("You can /clear now") starved on `marker: no marker`. Fixed to arm next to the written file itself (the hook input carries its path); the misplaced live marker was moved, and the watcher fired the full cycle within one pass (FIRE 09:25:13Z → fresh id `4aa5b19b` → reinject carried `0912-ff48` automatically).
- [x] 9.2 **Owner-write executor for fleet-held TUI agents (measured, FIXED 2026-09-13):** ownerd holds interactive `claude` TUIs (no `-p`) — `OwnerClient.write(label, …)` delivered Escape + `/clear\r` into a live agent and the full chain ran (clear → fresh session id `dcc59baa` → reinject fired). **Fix:** `watch-auto-clear.sh` has a second writer branch — when no tmux pane hosts the pid, the fleet roster (`OwnerClient.list_agents()`, matched by pid) supplies the label and the watcher writes ESC + C-U + `/clear\r` (C-U kills a half-typed input line — the first live fire landed on a pane where the user had `/clear` half-typed). First live fire 2026-09-13 08:46:52Z: the 528k bugfix session, ineligible all night, went eligible on the first pass of the new gate and was cleared end-to-end (FIRE → sent → fresh id `7ffc9ebc` on the same pid). 65 overnight `no tmux pane hosts pid` skips were this exact hole.
- [x] 9.3 **Token file is per-project, not per-session (seen in the first armed pass, FIXED 2026-09-13):** two sessions in one repo share `.set/handoff/.context-tokens` — the statusline renders of either overwrite it, so session B can read session A's 474k+ as its own. **Fix:** the statusline fragment writes `.context-tokens-<session8>` from the stdin `session_id`; the gate reads the per-session file when a session id is given and touches the shared name only for legacy session-less calls — a fresh shared file from ANOTHER session can no longer arm anyone (guarded by test).
- [x] 9.4 **Stale statusline file short-circuited the transcript fallback (measured 2026-09-13, FIXED):** `readTokens` returned `statusline-stale` on a stale-but-valid file instead of falling through — 1061 of 1742 armed-night verdicts starved on it while the sessions' own transcripts held the true numbers (the 528k bugfix session sat overnight, "Ready for /clear", unfired). Stale now falls through per the documented source order; "statusline-stale" is only reported when nothing pans out.
- [x] 9.5 **Session-start lookup skipped every record file (measured 2026-09-13, FIXED):** the old filter skipped any `~/.claude/sessions/` file whose name contains a dot — true of every `<pid>.json` — so the marker gate's start check NEVER ran. Two design findings came out of fixing it: (a) a fleet RESTORE keeps the session id and restarts the process, so the thread's own marker predates the new start — the comparison is now ANNOUNCEMENT in the gate detail, not a blocking verdict (blocking it was measured harmful: the restored 528k session would have been starved of its own armed handoff); (b) identity is the id: the start time is the earliest across a session's records, so a restored process cannot disown its marker.
- [x] 9.6 **Per-session opt-out (user ask 2026-09-13):** "disable auto-clear for THIS session" had no structural form — the agent cannot touch the watcher, and a promise not to write a handoff is fragile (a later turn arms it anyway). The gate now has a 5th gate: `.no-autoclear-<session8>` in the handoff dir blocks the clear whatever else holds. Create it by hand, or ask the agent to. Presence is the vote; the gate only obeys.
- [x] 9.7 **Auto-continue (user ask 2026-09-13: "why we do the clear and reload is to continue work"):** the cycle had a dead step 5 — after the automatic clear + reload the fresh session sat waiting for input. The watcher now takes `--auto-continue PROMPT` (+ `--continue-delay SEC`, default 20): after a successful automatic clear it delivers the continuation prompt through the same writer path (C-U first, then the prompt). Fires ONLY after the watcher's own clears — never after a manual /clear, where a human is at the keyboard. The consumer prompt tells the agent to read the full handoff and continue §5's first open step, stopping at §3 decision blocks. Armed 09:32:08Z (`auto-continue=on`). An accidental variant was already observed live before this: a background monitor that survived the clear re-invoked the fresh session on its own — designed now, not accidental.
- [x] 9.8 **Activation skill + two switch scopes (user ask 2026-09-13: "építsd, ki-be kapcsolható projekt és session szinten"):** new shipped skill `skills/auto-clear/SKILL.md` (installed by EVERY init, global installs included) — /auto-clear arms (state check → init --auto-clear → merge verification → watcher start with profile args → log-verified), /auto-clear off [project|session <id8>] creates the kill-switch file, /auto-clear status measures. Gate side: the optout gate now has TWO scopes — `.no-autoclear` (tree-wide) and `.no-autoclear-<session8>` (one session); the wider beats the narrower beats every other gate. 36/36 tests; deployed globally to ~/.claude/skills/auto-clear/ (hand-installed — the global handoff skill has drifted, so init --global was deliberately NOT run, §1 thread 5).
